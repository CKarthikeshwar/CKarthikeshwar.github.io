CK / Interview guide

Proof Verifier

Draw a proof by hand; Lean 4 checks it; plain-English feedback comes back.

30-second pitch

Proof Verifier is a web app where a maths student writes a discrete-maths proof by hand, one step per line. It reads the handwriting, translates each step into Lean 4, lets Lean actually check it, and tells the student in plain English what is verified, what is still missing and what is wrong. The point is that the feedback comes from a real proof checker accepting or rejecting steps, not from a chatbot's opinion.

  • The student draws on an Excalidraw canvas. Each finished line is sent to Gemini Flash-Lite, which reads the whole line in context. A local OCR model (mathnote-ocr) gives live previews and acts as the fallback.
  • A structure parser turns symbols and positions into an expression tree (exponents, fractions, subscripts).
  • The translator turns one step at a time into a Lean tactic block using few-shot examples plus lemmas retrieved from Mathlib.
  • Lean checks the statement, every earlier step and sorry for the rest. Result is closed (done), open (valid so far) or error (names the failing step).
  • A feedback layer restates Lean's goal state or error as a short plain-English message. Edit an earlier step and the later ones are translated and checked again.

Architecture and stack

  • Frontend: React + Vite + TypeScript, Excalidraw canvas, hosted on Vercel.
  • Vercel serverless functions (/api/lean, /api/recognize, /api/feedback) hold the API keys. The browser never talks to EC2 directly and no key ships in browser code.
  • Backend on one EC2 box: FastAPI services for Lean (Pantograph + Mathlib), recognition and translation, behind Caddy for HTTPS.
  • Python translation package with a retrieval module (Mathlib lemma search) and a sorry-skeleton assembler.
  • Shared data shapes live in contracts/ (stroke schema, symbol schema, expression tree, Lean interface, feedback interface) so tracks could be built in parallel.

Hard problems and what I learned

  • Compiles is not the same as faithful. Gemini turned "we prove both parts" into one long exact that closed the whole proof and swallowed later steps. It compiled, so nothing flagged it. Fixes: a prompt rule against tactics that finish more than the step, and a guard that sends a bare ring/simp that closed nothing back to be written as a have.
  • Cascading failures. After one failed step every later step said "earlier step hasn't been translated" and gave wrong advice about symbols. Now later steps are blocked without calling any backend and say which step they wait on.
  • Invented lemma names. Nat.odd_iff_not_even does not exist. Retrieval queries with the step text returned noise, so the lemma lookup needs a better query.
  • Student wording is harder than test wording. Test proofs say "Replace a with 2j"; students write a + b = 2j + 2k or "So n^2 is even". The 5/8 typed result is therefore optimistic.
  • Free-tier rate limits. Gemini 429s caused two "translator is busy" failures in the first run. The client does not retry yet.
  • Deployment pain. Mathlib gets OOM-killed on 1-2 GB instances, the Docker image took about 30 minutes to build, disk had to grow from 40 to 60 GB and an 8 GB swap was added.

Limitations to state honestly

  • No test on real handwritten proofs yet, only the owner's lines and synthetic ink. Clean Hershey-font strokes are the easy case.
  • V1 cannot detect a tactic that compiles but changes or swallows the student's step. The faithful flag in the research log is filled by hand.
  • One failed step blocks the rest of the proof until rewritten. Simple and honest, but harsh.
  • The Leanstral comparison was never run (no Mistral key); Gemini is the default by build order, not by head-to-head comparison.
  • Mobile is out of scope; desktop or tablet with a stylus.

What I would do next

  • Record real handwritten test proofs and measure recognition and translation end to end.
  • Build the faithfulness checker from the research plan: flag when a translation skips, merges or weakens a step even though it compiles. This is the genuinely under-studied part.
  • Add a repair loop that feeds the flagged issue back to the model, then test across two or three models.
  • Client retry and a paid or higher-quota key; improve retrieval queries; second wording of test proofs in student style.

Likely questions

Why Lean instead of just asking an LLM to check the proof?

An LLM can be confidently wrong. Lean is a kernel-checked verifier, so "verified" means something. The product claim is that the feedback comes from a real checker; a chat assistant cannot truthfully copy that.

What does sorry give you?

Lean treats it as a placeholder that still compiles. A file with translated steps followed by sorry is a valid skeleton, so we can report "valid so far, here is the remaining goal" instead of a hard failure. That powers the open state.

How do you tell translation errors from student errors?

Honestly, only partly. Feedback wording says "as translated" and the confirm step exists so the student can see what was read. Faithfulness is the main open research problem and I document it rather than hide it.

Why not fine-tune a model?

Existing data is mostly competition maths, not student-written proofs. With no dataset of the target style, few-shot plus retrieval was the cheaper first step. Fine-tuning a small model on a collected clean+noisy dataset is listed as an optional later phase.

How did you handle the cost of running Lean?

One long-lived Pantograph server with Mathlib imported once, checks of single files with no import line, prebuilt Mathlib cache. About 130-150 ms of Lean time per check.

How did you organise a 12-track project?

Each track has a spec with a checklist, open questions and a changelog entry for every decision. Tracks depend only on contracts (data shapes), so four tracks had zero dependencies and could start on day one. Branch and worktree per track.

What would break at scale?

A single EC2 box and free-tier Gemini quota. The next steps would be a queue and multiple Lean workers, caching of repeated checks, and a paid model quota.

What is the security model?

Keys only in Vercel server-side env vars; Lean service takes a shared key and is reachable only through the functions, which forward just two operations; SSH limited to my IP.
