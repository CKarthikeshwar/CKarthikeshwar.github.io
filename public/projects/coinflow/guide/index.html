CoinFlow: the technical guide

Written to be read once, top to bottom, the night before. It explains the app itself, so every concept (threads, databases, background work) is taught through something CoinFlow actually does. Facts come from the repository at version 2.1.0.

1. The pitch

30 secondsCoinFlow is an Android expense tracker where you never type a transaction. Your bank and UPI SMS already say what happened, so the app reads them on the phone, works out the amount, direction and account, and sends a notification. You tap Save, or review it quickly, and it's recorded. Everything happens on the device: there is no server, no login, and the SMS text is never stored. It is built with React Native and Expo in TypeScript, with a small Kotlin module for the Android SMS parts, and a SQLite database on the phone.
2 minutesFive ideas carry the whole app.
  1. Detect, don't ask. A broadcast receiver in Kotlin wakes the app when an SMS arrives, even if it is closed. A JavaScript task then parses it.
  2. Never guess, only remember. No machine learning. The only thing that pre-fills a category is what you chose last time for that same account.
  3. Local-first and private. A SQLite database on the phone, no network code outside an opt-in crash reporter, and a test that enforces it.
  4. Money is an integer. Every amount is stored as whole paise, so there are no floating-point errors.
  5. Layers with one job each. Pure logic (parser, maths) is separate from the database, which is separate from the screens, so each part can be tested alone.
Version 2 added "My accounts" (balances, card bills, transfers between your own accounts), and split payments that travel by plain SMS between two CoinFlow users.

Three ideas you must be able to explain

How React Native works. Your JavaScript runs on its own thread inside the app. It describes the UI, and React Native creates real Android views from that description. When JavaScript needs something only Android can do (read an SMS, post a notification), it calls into native code. The new architecture (newArchEnabled=true) lets JavaScript and native talk directly instead of through an older asynchronous message queue.

Why not Expo Go. Expo Go is a pre-built app that can run Expo projects, but it contains only Expo's standard native code. CoinFlow has its own Kotlin module, so it needs its own build, a "development build" made with expo run:android.

Why Android only. iOS and browsers do not let an app read SMS. The web build exists only to preview UI, and each screen shows an "Android only" notice there (*.web.tsx files).

3. One SMS, start to finish

This is the most important section. If you can narrate this flow with the reasons, you can answer most questions.

SMS arrives
  -> SmsReceiver.kt            (Android BroadcastReceiver, works even if the app is dead)
  -> CoinflowSmsHeadlessTaskService.kt   (starts a JavaScript engine with no UI)
  -> smsIngestTask()           (src/services/tasks/sms-ingest.ts)
       1  sender allowlist?     no  -> stop
       2  parseSms()            OTP / promo / request / foreign currency -> stop
       3  is it a transaction?  no  -> stop
       4  dedupe check          already seen -> stop
       5  save a Suggestion row (not yet a real transaction)
       6  look up the account's learned rule
       7  post a notification
       8  self-heal: re-post notifications that got lost
  -> user taps Save (or opens the Review Queue)
  -> a real Transaction row is written
  -> every screen showing that data refreshes by itself

Step by step, with the reason

  • The broadcast receiver. Android sends a system broadcast, SMS_RECEIVED, for every incoming text. A receiver declared in the manifest is started by Android even if the app is not running. That is the only way to be woken by an SMS. It has roughly 10 seconds, so it does almost nothing: it joins multi-part messages, takes the sender, body and timestamp, and hands them on.
  • The headless task. A "headless JS task" starts the JavaScript engine with no screen attached and runs one registered function by name, CoinflowSmsIngest, within a 30 second budget. This is why index.js imports src/services/tasks before the router: the registration must exist even when Android starts the app just to run this task.
  • Sender allowlist. Indian bank SMS come from ids like AD-HDFCBK: a telecom prefix, a dash, then the bank's id. The prefix is stripped and the rest compared with a curated list (HDFC, SBI, ICICI, Axis, Kotak, Paytm, PhonePe, GPay and others). Random spam never reaches the parser. The list is hand-edited in src/constants/sms-senders.ts.
  • Parse, then gate. parseSms is a pure function (section 4). It returns "ignored, here is why" or "a transaction with these fields".
  • Dedupe. The key is sha256(sender | amount | minute | direction). If the same message is processed twice (a retry, or one of our backup detection paths), the key already exists and nothing is created. Both the suggestion and transaction tables carry the key, since a suggestion may already have been cleaned up.
  • Suggestion, not transaction. Detected items are saved as a suggestion with status pending. Only your confirmation turns one into a transaction. This keeps a wrong guess from polluting your real ledger.
  • Notification. If the account has a learned category, the notification offers a one-tap Save. Otherwise it only opens the review sheet. Tapping Save runs in a background task, so the app need not open.
  • Self-heal. If the task was killed after saving the suggestion but before notifying, the next run notices a pending suggestion with no notification and posts it.
  • Live refresh. SQLite is opened with enableChangeListener: true and screens read through Drizzle's useLiveQuery. Any write, including one from the background task, re-runs the queries on screen. Nothing calls "refetch".
Design rules inside this flowThe ingest function never throws: Android may run it under tight limits, and a crash could make the OS less willing to wake the app again, so failures are logged by error type only and swallowed. The SMS body is never written to disk or logs, only the fields extracted from it. It reuses the same repository functions as the UI, so a notification Save and an in-app Save cannot behave differently.

4. How the parser reads a message

The parser lives in src/domain/parser/ and imports nothing from React Native or Expo. That is on purpose: a function that takes text and returns a result can be tested against hundreds of real message formats without running the app.

Order of the checks

  1. Sender gate (allowlist above).
  2. Ignore gate (ignore-rules.ts), first match wins: OTP; promo (words like "offer", "loan", "discount", or a link with no money verb); balance-only; a money request ("collect request"); foreign currency without an INR amount; not yet settled ("will be credited", "is pending"). It runs before extraction so a promo saying "₹500 cashback" is never read as a ₹500 transaction.
  3. Extraction (extract.ts), regular expressions that find the amount, the direction, the other party, and the payment method (UPI is detected from a VPA like name@bank).
  4. Transaction gate: if neither an amount nor a direction was found, it is not a transaction.

The hard part: picking the right amount and direction

A real SMS can say "Rs 500 debited ... Avl bal Rs 12,340". Two amounts, and it could even contain both "debit" and "credit". The rule is closest to a direction word wins:

  • One amount: that is it. Several amounts but no direction word: take the first.
  • Several amounts and a direction word: choose the amount fewest characters from any direction word. A bank writes the amount next to the verb ("Rs 500 debited"), not next to the balance.
  • Both debit and credit words: choose whichever is nearer the chosen amount. If exactly tied, flag it ambiguous and let the user decide.

Details that show you understand it

  • Paise as integers. The amount string is split at the decimal point and converted to an integer count of paise. It is never parsed into a floating-point rupee value. Indian digit grouping (1,00,000) is handled by the regex.
  • Sanity ceiling. Amounts above ₹1 crore, or zero, are flagged out of range instead of trusted.
  • Time is the receive time. occurredAt is when the phone received the SMS, not a time parsed out of the text, because banks format timestamps inconsistently.
  • No confidence score. A field is either found or null. It is left blank for you to fill, never guessed.
  • Test corpus. The parser is tested against a fixture file of anonymised real bank messages. Each new bank format that fails becomes a new test case.

5. Making detection reliable

The broadcast alone is not enough, and this is a good story to tell. During testing, a message was missed. The cause: another app that also holds the SMS permission (Truecaller is an example) can register at the same priority and call abortBroadcast(), so CoinFlow's receiver never runs. No error, no log. The fix was to stop depending on one signal.

PathHow it worksLimit
1. BroadcastSmsReceiver, real time.Can be aborted by another app.
2. Store watcherA JobScheduler job triggered by a change to Android's shared SMS store. An app can abort a broadcast but cannot stop the message being written to the store.A content-trigger job fires once, so it re-arms itself first thing. It does not survive a reboot, so JavaScript re-arms it on launch. Doze can delay it.
3. App-open sweepOn launch and every return to the foreground, re-read the last 48 hours of the inbox and run each message through the same ingest function. Notifications are skipped because you are already looking.Only runs when the app is opened.
4. Periodic taskA background task about every 12 hours, doing the same sweep with notifications on.The OS batches and delays these.

Why this is safe to run repeatedly: all four paths feed the same smsIngestTask, and the dedupe key makes processing a message twice harmless. That property is called idempotency. A fixed 48-hour lookback was chosen over a saved "last synced" marker so there are no cursor or clock bugs to worry about.

An Android 12+ detail from the code: the store watcher runs the JavaScript task itself instead of calling startService, because an idle background app is refused with BackgroundServiceStartNotAllowedException (seen on a Samsung phone running Android 16).

6. The database

Tables that matter

TableHolds
transactionConfirmed money movements: amount in paise, direction, type (expense, income, transfer, refund, reimbursement), category, payment method, account, note, time, source (manual or sms), deletedAt.
suggestionSMS-detected items waiting for you. Status pending, confirmed or dismissed. Unique dedupeKey.
category9 default expense categories plus Uncategorized, a few income ones, and your own. Types: system, default, custom.
account_ruleThe account memory: for one normalised account, the last category, income category, note and payment method.
my_account, account_balanceV2: your own bank, card, wallet and cash accounts, and card limits and due dates.
person, split, split_share, split_request_in, settlementV2: people, split payments, each person's share, requests received, and payments that settle them.
app_settingSmall key-value settings, stored as JSON.

Design choices to defend

  • Money is an integer count of paise. Floating point cannot represent 0.1 exactly, so sums drift (0.1 + 0.2 gives 0.30000000000000004). Integers add exactly. Columns even have CHECK (amount > 0) constraints.
  • Soft delete and undo. Deleting sets deletedAt instead of removing the row, which allows the Undo snackbar. A cleanup purges rows after the grace period.
  • Indexes. On the columns the screens filter and sort by, like (deletedAt, occurredAt) for the ledger, plus category, account and dedupe key.
  • Foreign keys are enforced (PRAGMA foreign_keys = ON), so deleting a category sets categoryId to null on transactions instead of leaving a dangling reference.
  • WAL mode lets a screen read while the background task writes.
  • Synchronous SQLite API. The UI and the headless task use the same code path, with no async and sync variants to keep aligned. SQLite is local and fast, so the main thread is not blocked noticeably.
  • Migrations. drizzle-kit generate compares schema.ts with the previous state and writes a SQL migration, committed to the repo. At startup MigrationGate applies pending ones before rendering anything, with the splash screen still showing. If migrations fail it shows a recovery screen with "Try again" and "Export a copy", and never wipes data silently.
  • Repository pattern. Only src/db/repositories/* runs queries. Screens call repository functions. Derived fields (type from direction, the normalised account key, search text) are computed in one place, so every caller gets them.
  • Search uses SQLite FTS5 (full-text search) when available.

7. Account memory

Many apps guess a category from keywords or a trained model. CoinFlow does not. The only thing that pre-fills a category is: have you confirmed a transaction from this exact account before, and what did you choose?

  • Bank SMS never write the same account the same way twice (reference numbers change). normalize.ts lower-cases the string and strips masked digits, long references and punctuation, so HDFC A/c XX1234 REF001 and ...REF002 become the same key. UPI ids keep their @ . _ - characters, because those are part of the identity.
  • Each key has one account_rule row: expense category, income category (the same person can both be paid by you and pay you back), last note, last payment method, and a hit count. Confirming a transaction updates it.
  • A rule is known if it has a remembered category for that direction or a note. Known accounts get a one-tap Save; new ones need a review.
  • No account parsed, or no rule, means Uncategorized with a blank note. It never guesses.

Why defend this: it is explainable and predictable. You can always say exactly why a category was chosen, and a wrong guess cannot silently corrupt your data. The trade-off is a cold start: the first transaction from each account needs a manual choice.

8. Version 2: accounts, transfers, splits

My accounts and balances

  • When an SMS names a bank and the last 4 digits, the app auto-creates a my_account with matchKey = bank + last4, which is unique. A card SMS creates a credit-card account.
  • Balance is the sum of the account's own transactions, credits plus and debits minus, starting from zero. It is never read from the bank's "available balance" text. That keeps one consistent definition and means the figure is never "unknown", though it is not the bank's real balance. Say this directly if asked.
  • Credit-card statements update the card's due date and amount, and the app schedules a reminder at 10:00, two days before the due date.

Transfers between your own accounts

Moving ₹5,000 from savings to a card creates a debit on one account and a credit on another. Counting both as spending and income would be wrong. matchTransfer looks for a twin: opposite direction, same amount, different account, within 15 minutes. If exactly one match exists in both directions and at least one side came from an SMS, they are linked automatically as a transfer. If it is ambiguous, the app asks you. The principle is stated in the code: a wrong silent link hides real spending, a missed link only shows two rows, so it errs towards asking.

Split payments

  • You split one transaction among people. Each person's share is a positive whole number of paise. Your own share is never stored; it is derived as amount - sum of shares, so the totals can never disagree.
  • Percent splits are converted to paise with the largest-remainder method, so the shares always add up exactly to the total (₹100 split three ways gives 3334 + 3333 + 3333 paise, not three times 33.33).
  • The request travels as an ordinary SMS, with no server: Name requests Rs 450.00 for Momos (CoinFlow split). {cf1|ab2cd3|45000|Momos}. The sentence is for a human without the app. The {cf1|ref|paise|note} token is what the other CoinFlow reads. The same ref with a new amount updates the request, and amount 0 withdraws it.
  • The text uses Rs, not ₹, because ₹ is outside the GSM-7 SMS alphabet and would force a 70-character UCS-2 message instead of 160.
  • Incoming requests are untrusted input. Anyone can send that text, so it must come from a numeric sender (banks use alphanumeric ids, so a bank text can never be mistaken for one), match a strict grammar, stay within bounds and rate limits, and is idempotent per (sender, ref). Nothing is accepted, paid or replied to automatically.
  • SEND_SMS is asked for only at the moment you press Send. If refused, the app opens each pre-filled message in your SMS app instead of sending silently.

Widgets

Home-screen widgets (balance, review queue) are native Kotlin. JavaScript computes a snapshot using the same query as the Analytics screen, so the two can never disagree, and hands it to the native widget providers. The snapshot is also refreshed at the end of every background task.

9. How the code is organised

src/app/        screens (expo-router). Thin: mostly wiring
src/features/   the real screen content, grouped by feature
src/domain/     pure logic: parser, categorize, normalize, analytics, split, balance
src/db/         schema, client, migrations, repositories (the only code that queries)
src/services/   background tasks, notifications, SMS wrapper, splits, widgets, crash
src/stores/     Zustand: in-memory UI state only
src/ui/         reusable components (Button, Card, TextField...)
modules/coinflow-sms/   the Kotlin native module
  • Dependency direction. Screens call features, features call repositories and domain, domain imports nothing from the framework. Pure code is easy to test, and the same domain code runs in the UI and the headless task.
  • One sheet for three jobs. Add, Edit and Confirm are the same bottom-sheet component in different modes, because they share almost every field. One shared sheet host renders sheets, opened from anywhere through a small registry store.
  • State has two homes. Data you must keep lives in SQLite. Things like half-typed form text live in Zustand and vanish when the app closes. Before adding state, ask which kind it is.
  • Analytics. SQL aggregates the rows; the pure functions in domain/analytics.ts compute percent change, daily buckets, mean and median spend and the chart scale; d3 shapes drawn with react-native-svg render the charts. Days are local-device days, not UTC.
  • Startup order: index.js registers background tasks, then the root layout waits for fonts, MigrationGate migrates, seeds default categories and purges soft-deleted rows, and only then does the navigator choose onboarding or the tabs.

10. Privacy and permissions

  • No network, and a test proves it. no-network.test.ts scans domain, db, features and services and fails if any file makes a network call. The only exception is services/crash/.
  • Crash reporting is opt-in. Until you enable it in Settings no Sentry transport object exists. When on, events pass through scrubbing (redactError in the logger, then Sentry's beforeSend and beforeBreadcrumb) that removes anything resembling money, accounts or UPI ids. Logs record error type names only, never messages, since messages could contain SMS text.
  • No SMS text stored. The body is used in memory, and only parsed fields are saved.
  • Permissions: RECEIVE_SMS and READ_SMS for detection; SEND_SMS optional and just in time for split requests; contacts only when you choose someone to split with, and WRITE_CONTACTS is explicitly blocked; notifications.
  • Getting data out: export as JSON, CSV or a raw database copy through the Android share sheet. You choose where it goes; the app uploads nothing. There is no import.
  • Honest caveat: the SMS permission is sensitive. Google Play restricts which apps may request it, so expect a question on why the app is distributed as an APK; answer with what you actually did.

11. Testing and shipping

  • Tests: about 126 test files with Jest and Testing Library. The weight is on pure logic: the parser corpus, categorize and normalize, split arithmetic, transfer matching, balance, analytics. Plus repository tests, component tests and the no-network guard. One Maestro flow covers end to end.
  • Checks before a build: npm run typecheck (tsc --noEmit), npm run lint, npm test.
  • Build: npm run android makes a development build, installs it and starts Metro, the dev server that bundles the JavaScript and reloads it live. Editing Kotlin needs a full native rebuild; editing TypeScript does not.
  • Release: pushing a tag such as v2.1.0 triggers a GitHub Actions workflow. It runs expo prebuild to generate the android/ folder (never committed), injects a signing config from secrets with a small config plugin, builds with Gradle, and attaches a signed coinflow.apk to a GitHub Release. The permanent link releases/latest/download/coinflow.apk always serves the newest one.
  • Why signing matters: Android refuses to install an update signed with a different key, so the same keystore must be used every time.

12. Limitations, honestly

Naming these yourself reads as understanding, not weakness.

  • Regex parsing is brittle. A bank changing its wording can break detection until a pattern is added. That is why there is a fixture corpus. The alternative, a language model, would need either a network or a heavy on-device model, which conflicts with the privacy goal.
  • The sender list is hand-curated. A bank missing from it is invisible until the list is edited.
  • Android only, by platform rules.
  • Balance is computed from your transactions, not the bank's figure, so it is only right if every transaction is recorded.
  • Background timing is up to Android. Doze and app standby can delay the store watcher and periodic sweep, so detection is not guaranteed instant.
  • Notifications do not visually stack. The installed expo-notifications does not expose Android's grouping call, and fixing it would need more native code. Accepted gap.
  • Known gap: the "restore a lost notification" self-heal runs when a new SMS arrives, not on every launch, so a notification lost to a reboot returns only at the next SMS (the suggestion itself is never lost).
  • No import, no light theme, no iOS support. Split requests rely on SMS, so they need both people to run CoinFlow and are not guaranteed delivered.

13. Questions they will ask

Open each, answer out loud first, then compare. These are the questions an interviewer would raise from the material above.

How does your app detect a transaction when it is closed?
A Kotlin BroadcastReceiver declared in the manifest is started by Android for every incoming SMS, even if the app is dead. It passes the sender, body and time to a headless JS service that boots the JavaScript engine with no UI and runs a registered task, smsIngestTask. That task filters, parses, saves a suggestion and posts a notification. The registration is imported first in index.js so it exists when Android starts the app only for this.
Why didn't you just write the whole app in Kotlin?
Most of the app is ordinary UI and logic, where React Native is faster to build and one codebase is easier to test. Only the parts that need Android system access went native, as a small module. The logic that matters (parser, maths) is plain TypeScript, so it is also unit-testable without a device.
Why SQLite and not a cloud database?
The privacy promise is that financial data never leaves the phone. A local database gives that, works offline, and needs no server or login. The trade-off is no automatic backup or multi-device sync, so I added export (JSON, CSV, raw copy).
Why store money as integers?
Floating-point numbers cannot represent most decimals exactly, so sums drift. Storing whole paise and doing integer arithmetic is exact. I convert the text amount to paise by splitting at the decimal point, never through a float.
How does the parser pick the right amount when a message has two?
It finds every amount and every debit or credit word, then picks the amount with the smallest character distance to a direction word, since banks write "Rs 500 debited" together while the balance sits elsewhere. If both debit and credit words appear, the nearer one to that amount decides, and an exact tie is flagged ambiguous rather than guessed.
How do you avoid duplicate transactions?
Each detected SMS gets a SHA-256 key from sender, amount, minute and direction. The suggestion table has a unique index on it, and the transaction table stores it too. All four detection paths call the same ingest function, so processing a message twice is harmless: the operation is idempotent.
Is your categorisation machine learning?
No, deliberately. It is a lookup: the category you last confirmed for that normalised account. It is explainable, never silently wrong, and works offline with no model. The cost is that the first transaction from a new account needs a manual choice.
What is a headless JS task, and what is its limit?
JavaScript running without any screen, started by native code to do one job. It has a time budget (30 seconds for SMS ingest), must not rely on React state, and has to open its own database connection. So it must be fast, must never throw, and shares only the database and pure logic with the UI.
What if another app blocks the SMS broadcast?
That happened in testing: an app with the same permission can abort the broadcast before mine runs. So I added a JobScheduler trigger on the SMS store itself (the message is still written there), a sweep of the last 48 hours whenever the app opens, and a periodic background sweep. They all feed the same ingest function, and dedupe makes the overlap safe.
How do screens update when the background task writes data?
SQLite is opened with a change listener, and screens read through useLiveQuery, which re-runs the query when a write happens anywhere. The write could be from the UI or from the headless task. No screen refetches manually.
Why a Suggestion table instead of writing transactions straight away?
A detection can be wrong or partial (a missing amount, an unusual message). Keeping it as a pending suggestion means nothing reaches the real ledger or analytics until you confirm it, and dismissing it leaves no trace.
What is the repository pattern and why use it?
All queries for a table live in one file, and nothing else touches the database directly. Derived fields are computed in one place, behaviour is consistent, and changing storage later means editing one file. Screens and background tasks call the same functions.
How do migrations work?
I change schema.ts, run drizzle-kit generate, and it writes a SQL migration comparing old and new schema. Migrations are committed. On launch MigrationGate applies pending ones before any screen renders, so existing users' data is upgraded in place, not erased.
How do you know a transfer between your own accounts is not spending?
I look for a twin transaction: opposite direction, same amount, different account, within 15 minutes. If there is exactly one candidate both ways and one side came from an SMS, I link them automatically. Otherwise I ask. A wrong silent link would hide real spending; a missed one only shows two rows.
How can two phones split a bill without a server?
The request is a normal SMS with a machine-readable token at the end. The receiving CoinFlow recognises the token, and shows a request you can accept or reject. Nothing is acted on automatically. Because anyone could send such a text, the receiver only trusts a numeric sender, a strict format, bounded values and rate limits.
Why use "Rs" instead of the rupee sign in the request?
The rupee sign is not in the GSM-7 SMS alphabet. One such character switches the whole message to UCS-2, cutting a segment from 160 characters to 70, which means more segments and a higher chance of failure. Plain text keeps it compact.
How do you prove the app makes no network requests?
There is a test that scans the source folders for network calls and fails if it finds one outside the crash-reporting folder. It is a static check, so a future mistake is caught by the tests and not by someone remembering.
What about user privacy if crash reporting is on?
It is off by default and opt-in. When on, errors go through two layers of scrubbing that remove anything that looks like money, accounts or UPI ids, and the logger only records the error type name, not its message.
Why can't this be on iOS or the web?
Neither platform allows an app to read the user's SMS, for privacy reasons enforced by Apple and browsers. The web build only previews the UI with an "Android only" notice.
Why can't you use Expo Go?
Expo Go contains only Expo's standard native modules. Our SMS module is custom Kotlin, so we need our own development build.
How do you release it?
Pushing a version tag runs a GitHub Actions workflow that generates the Android project, applies the signing config from encrypted secrets, builds a signed APK with Gradle, and attaches it to a GitHub Release under a fixed filename, so one download link always points to the latest.
What would you improve next?
Sample answer, adjust to what you believe: More bank formats and a way to add senders without editing code; import to complement export; running the notification self-heal on every launch; and, if I could accept some on-device model, a fallback for messages the regex cannot read.
Tell me about a bug you hit.
A good one from the code and its comments: the silently missing SMS caused by another app aborting the broadcast. It left no log because no code of mine ran. Finding it needed on-device testing, and the fix was to depend on several independent signals instead of one.
